# Meta-Harness — Harnesseed 自身はこう作られた（正典）

これは作文ではない。v1.0 のビルド過程の一次記録（`../docs/bootstrap-log/`）から蒸留した、
「ハーネスをハーネスエンジニアリングで作る」ための再現可能な型である。各主張には実記録への
参照を付す。

## 型1: 作る前に調べ、調べたものを疑う

最初にやったのはコードではなくトレンド調査だった
（`docs/bootstrap-log/2026-06-18-trend-scout-0.md`）。4アングルの fan-out 調査に
**敵対的検証を対にした**ことで、「PostToolUse は block できる」等の誇張を出荷前に落とせた。
検証されていない知見はストックに入れない — この規律がそのまま `/harnesseed:scout` の仕様になった。

## 型2: 設計は敵対的レビューで壊してから実装する

最初の設計は「フックがユーザーに質問する」を前提にしていたが、5レンズのクリティーク
（`docs/bootstrap-log/2026-06-18-design-critique-1.md`）がそれをプラットフォーム上不可能と
特定し、検知（フック）/質問（モデル）/作業（スキル）の分離に組み直させた。フルv1.0 spec も
find→verify 2段のレビュー（`docs/bootstrap-log/2026-07-13-design-critique-2.md`、
確認27件）を通ってから実装に入った。**レビューは工程であって儀式ではない**。

## 型3: 指摘自体も検証する（find → verify）

クリティーク#2 では finder の指摘30件に懐疑的検証者を1体ずつ当て、3件を反証で落とし、
残りの fix の不正確な部分も補正した。#3（実装レビュー、
`docs/bootstrap-log/2026-07-13-p1-critique-3.md`）では検証者に**隔離環境での実再現**を
要求した結果、反証は0件 — findings が実測ベースになるほどレビューの信頼度は上がる。

## 型4: プランは出発点であって根拠ではない

実装レビュー（同上 #3）は、承認済みプランのコード例そのものに由来する欠陥を複数捕捉した
（機械可読でない trailer・cwd 相対のマーカー書き込み・CI ゲートの `|| true`）。
「プランに書いてあった」は品質の根拠にならない。実物を、実物として、レビューする。

## 型5: 決定的チェックを最優先し、判定の階層を守る

v1.0 の検証は3層でできている: ①決定的（hash 照合・フィクスチャテスト・CI — 自動 revert に
接続できる唯一の層）②LLM 判定（挙動シナリオ — advisory のみ）③人間（承認ゲート — 最後の砦）。
この階層は philosophy.md の「検証はモデルより強い」の実装形であり、`blueprint/evals/` と
`/harnesseed:grow` の構造にそのまま現れている。

## 型6: 記録が次の自分を作る

このファイルは、開発中に書き溜めた bootstrap-log から**事後に**蒸留された（先に書くと
「存在しないビルド過程の作文」になる — それは初期設計のクリティーク#1 が却下した案だった）。
記録 → 蒸留 → 正典化、の順番を守ること。growth-log / checkups / bootstrap-log が
将来の drift review と次の設計判断の一次資料になる。
